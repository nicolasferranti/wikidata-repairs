# wikidata-repairs
This repository contains the resources generated by the paper "Formalizing Repairs for Wikidata Constraint Violations: A Taxonomy and Empirical Analysis", which presents formalizations of both violations and repairs in Wikidata, as well as a taxonomy of repairs historically performed by the Wikidata community. The paper also presents an empirical analysis of historical repairs to identify the existence of the mapped repair patterns.

The repository provides a step-by-step procedure to reproduce the experiments, which generally consists of:
1. Preparing the data:
1.1. Download two HDT Wikidata snapshots to be compared.
1.2. Install Java libraries to query HDT files.
1.3. Execute SPARQL queries to retrieve violations.
2. Calculating diffs between historical violations to identify historical repairs.
3. Analyzing repairs:
3.1. Set up a qEndpoint instance to test query patterns.
3.2. Execute scripts to extract constraint instances and use the repair files as input to calculate basic T-box repair patterns.
3.3. Use Jupyter Notebooks to query the qEndpoint instance and find specific A-box and T-box repairs.

```bash
.
├── datasets/                                   # Repair datasets (.csv) for all the analyzed constraint types
│
├── scripts/                                    # Folder with the scripts used for the experiments
│   ├── inconsistencies_collector/              # Folder to store the downloaded hdt snapshots, hdt-java, and the violation sets                
│   │   └── violation_queries/                  # A set of SPARQL queries (in .rq files) to extract constraint violations
│   │   
│   ├── repair_analyzer_notebooks/                  
│   │   ├── *_analyzer.ipynb                    # Jupyter notebooks with the methods to capture repair patterns
│   │   │
│   │   └── t-box repairs analyzer/             # Folder with a constraints relational db and a Python script to analyze basic T-box changes
│   │       │   
│   │       └── constraint_instances_queries/   # A set of SPARQL queries (in .rq files) to extract constraints and their qualifier sets to validate T-box changes
│   └── repair_generator/                       # Folder with scripts to generate the repair sets                
│
└── README.md                                   # Project overview and instructions
```

# Step 1: Inconsistencies collector

## 1.1: Finding Wikidata HDT Snapshots
The first step consists of downloading and preparing the resources to extract the violations and repairs.

Our experiments used two snapshots: 2019-06-19 and 2023-05-12; both were collected from the list available at [www.rdfhdt.org/datasets/](https://www.rdfhdt.org/datasets/), but the same procedure works for comparing any two HDT snapshots of Wikidata's latest-all dumps, available at [https://dumps.wikimedia.org/wikidatawiki/entities/](https://dumps.wikimedia.org/wikidatawiki/entities/).   

Let's use the folder ``scripts/inconsistencies_collector`` to store the snapshots:

```
$ cd scripts/inconsistencies_collector
```
Now download the *.hdt files in this folder. After downloading the files, the folder should contain two snapshots, e.g.: latest-all-19-Jun-2019.hdt and latest-all-12-May-2023.hdt

## 1.2: Installing hdt-java
To run the SPARQL queries and extract the violations, we first need to install the HDT-Java library, which provides tools for working with HDT files.

Installation:
```
$ git clone https://github.com/rdfhdt/hdt-java.git
$ cd hdt-java
```

Use ``mvn install`` to let Apache Maven install the required jars in your system.

You can also run ``mvn assembly:single`` under hdt-java-package to generate a distribution directory with all the jars and launcher scripts:
```
$ cd hdt-java-package
$ mvn assembly:single
```

Now you should be able to see the file ``scripts/inconsistencies_collector/hdt-java/hdt-jena/bin/hdtsparql.sh``.

You can test it by running a simple query, for instance:

```
$ cd ../..
$ sh hdt-java/hdt-jena/bin/hdtsparql.sh latest-all-19-Jun-2019.hdt "SELECT * {?S ?P []} LIMIT 1"
```

## 1.3 Executing SPARQL queries to retrieve violations

Once this is done, we can execute `hdtsparql.sh` to extract all the violations of a given snapshot for a given constraint type via a SPARQL query. All our SPARQL queries are available in the folder ``scripts/inconsistencies_collector/violation_queries``. We will use the None-of constraint as an example:

```
$ hdt-java/hdt-jena/bin/hdtsparql.sh latest-all-19-Jun-2019.hdt "$(<violation_queries/none_of_violations_query.rq)" > none_of_violations_2019.txt &
```

and the same for the second snapshot:
```
$ hdt-java/hdt-jena/bin/hdtsparql.sh latest-all-12-May-2023.hdt "$(<violation_queries/none_of_violations_query.rq)" > none_of_violations_2023.txt &
```

this will then generate two files ``none_of_violations_2019.txt`` and ``none_of_violations_2023.txt``, which we will use to extract repairs.

# Step 2: Extracting repairs

We are now ready to compare the violation sets and get the repairs, which are basically rows that appeared in 2019 and didn't appear in 2023. 
On the folder ``scripts/repair_generator``, run:

```
python repair_finder_diff.py ../inconsistencies_collector/none_of_violations_2019.txt ../inconsistencies_collector/none_of_violations_2023.txt none_of_repairs.csv
```

# Step 3: Repair Analyzer

To extract the reasons behind the repairs, it is necessary to execute multiple queries testing the existence/absence of different triple patterns.
In this step, using the same approach as in 1.3 would lead to a more time-consuming process because we now have multiple requests to validate specific patterns. Therefore, we loaded the HDT snapshots into [qEndpoint](https://github.com/the-qa-company/qEndpoint) (a scalable triple store that can be used as a standalone SPARQL endpoint) and proceeded with the scripts to find T-box and A-box repairs.

Example Dockerfile for loading a snapshot into qEndpoint:
```
FROM qacompany/qendpoint

ARG WIKIDATA_YEAR=2023
RUN echo "Building image for WIKIDATA $WIKIDATA_YEAR"

WORKDIR /app

COPY wikidata-prefixes.sparql ./qendpoint/prefixes.sparql
COPY repo_model.ttl ./qendpoint/repo_model.ttl
COPY wikidata_${WIKIDATA_YEAR}.properties ./wikidata.properties

EXPOSE 1234

ENTRYPOINT java -jar -Xmx24G qendpoint.jar --spring.config.location=./wikidata.properties
```

## 3.1 T-box basic repairs

Once the qEndpoint docker containers are set up, the T-box analysis begins with querying the constraint instances on both endpoints and generating a sqlite database to store changes on the constraints.
In the folder ``scripts/repair_analyzer_notebooks/t-box repairs analyzer``, set the URLs on file ``constraint_data_db_generator.py``:

```
QUERIES_FOLDER = "constraint_instances_queries"   # Folder containing your constraint_instances *.rq QUERY files
DB_FILE = "constraints.db"
ENDPOINT_2019 = "BASE_URL/wd2019"
ENDPOINT_2023 = "BASE_URL/wd2023"
```

And now execute the script to generate the constraint changes db:
```
$ python repair_constraints_collector.py
```

or just unzip the already provided ``constraint.db.zip`` to have the list of changes from 2019-2023. T-box changes can now be extracted by executing the script ``t-box_repairs_analyzer.py``.
This step tests: constraint deletion, deprecation of the constraint, and base statement subject added as an exception to the constraint. As well as getting some specific constraint qualifiers to be used later on.

## 3.2 A-box repairs and T-box specific

The output of step 3.1 can now be used as an input for the corresponding analyzer file available on ``repair_analyzer_notebooks/*_analyzer.ipynb`` which will test A-box repairs and T-box specific repairs.
